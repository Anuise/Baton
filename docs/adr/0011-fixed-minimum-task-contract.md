# ADR-0011：固定最小派工契約與分類補充

- 來源識別：DR-20261022-03
- 狀態：已確認（使用者核准，2026-10-22）；實作未查驗，欄位映射與流程待驗證
- 來源：[issue #3](https://github.com/Anuise/issue-orchestrator/issues/3) §17 DR-20261022-03；§3.5、§15.13
- Spec 對應：[spec.md](../../.scratch/platform-rebuild-v1/spec.md) 的 User Stories 26–27、35

## 背景

不同類型的 Worker（研究、文件、實作、審查）需要明確知道被委託什麼、做到哪裡算完成，否則完成標準會不一致，交接時也沒有依據。但要求使用者逐欄填寫會增加負擔，要求所有工作走完整軟體開發流程又不適合研究與文件工作。

## 決策

採 A「固定最小契約，依工作補充」：

- 所有 Task 使用同一份六項最小契約，由 Controller 整理，使用者不必逐欄填寫：（1）目標；（2）輸入與依據；（3）範圍與限制；（4）預期成果；（5）完成與驗證條件；（6）阻礙處理。依工作類型補充必要內容。
- 可引用既有政策、設定、Stage 或成果而不重複抄寫，但須保存可解析的引用與適用版本。確實不適用的欄位明示理由，未知事項標為未知，不能以空值、任意預設或假設冒充已確認。
- Runtime 在啟動准入前檢查必要欄位、引用可用性、版本、相依與授權。欄位齊全不代表語意正確，也不代表成果已通過。
- 契約不完整就不派工，先由 Controller 補足或依裁定規則詢問；可另建契約完整的調查 Task，但不能藉此繞過未決的產品取捨。
- 執行中契約變更須保存版本並依既有相依與 Gate 規則處理。成果回報對應契約版本、實際成果、證據與未完成事項；程序退出或 Worker 宣稱成功不等於 Task 完成。
- Worker 發現歧義或衝突時回報，不自行擴權或改寫完成標準。

## 替代方案

自由文字委託，缺漏由 Worker 追問：派工較快，但較晚發現歧義，增加完成標準不一致與交接成本。

## 後果

- 增加整理契約、解析引用與版本管理的成本。
- 結構檢查不保證語意正確。
- 必須防止空欄位被當成完整、引用失效、需求被當成假設，以及 Worker 自行修改驗收標準。
- 不新增權限，也不要求每個 Task 人工批准；特定工作類型的詳細範本不在此決策內。
