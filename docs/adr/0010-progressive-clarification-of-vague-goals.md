# ADR-0010：模糊目標的漸進釐清與拆工

- 來源識別：DR-20261022-02
- 狀態：已確認（使用者核准，2026-10-22）；實作未查驗，行為與整合驗證待完成
- 來源：[issue #3](https://github.com/Anuise/issue-orchestrator/issues/3) §17 DR-20261022-02；§8.3「模糊目標的漸進拆工」、§15.12
- Spec 對應：[spec.md](../../.scratch/platform-rebuild-v1/spec.md) 的 User Stories 21–23

## 背景

使用者提出的目標常常不完整。若要求先確認完整需求與完整計畫才能派工，會增加等待；但若在資訊不足時就虛構完整需求，又會把假設當成需求，或以「研究」名義偷跑未授權的實作。

## 決策

採 A「邊釐清、邊調查」：

- Controller 先整理已確認的目標、限制、成功條件、未知事項與假設；資訊缺少時明確標示，不虛構完整需求，也不一次排定全部工作。
- 影響產品方向、使用者價值或操作授權的問題交給使用者裁定，優先詢問會阻擋下一步的關鍵問題。
- 不依賴未決答案的研究或實驗，可在既有委託、授權與預算內先派給 Worker；已具備明確輸入、預期成果與可驗收完成條件的部分，符合設計、審查與驗收門檻後可開始實作。依賴未決答案的部分保持等待。
- Worker 回報後，Controller 區分「已證實資訊」與「仍未驗證的假設」，更新 Project Brief、Decision Map 與受影響工作；調查無法解決的產品取捨附證據送裁定。
- 無法取得證據、調查失敗或預算不足時保存缺口與原因，不宣稱已解決，也不無限重試。後續答案與既有工作不一致時，依版本與相依規則阻擋或重驗受影響部分，獨立工作繼續，不私改需求讓成果通過。

## 替代方案

先確認完整需求與計畫再派工：較易掌握全貌，但增加等待，且調查後仍可能重排。

## 後果

- 部分調查可能因方向改變而無法沿用。
- 需要額外的版本、相依與返工管理成本。
- 必須防止「假設被當成需求」「研究變相實作」與「無限調查」。
- 不新增任何權限，也不要求每個 Task 重新批准；其他拆工粒度與排程政策依既有規格。
