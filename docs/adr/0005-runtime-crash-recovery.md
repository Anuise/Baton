# ADR-0005：Runtime 意外崩潰後的自動恢復

- 來源識別：DR-20261021-05
- 狀態：已確認（使用者核准，2026-10-21）；Windows 實作與時間參數有效性為 Validation Required，尚未驗證
- 來源：[issue #3](https://github.com/Anuise/issue-orchestrator/issues/3) §17 DR-20261021-05；§1.2、§3.3、§11.4、§12.5、§15.7
- Spec 對應：[spec.md](../../.scratch/platform-rebuild-v1/spec.md) 的 D-16（預算）、D-31（計時參數）、User Stories 79–80、84

## 背景

長任務在背景執行時，Runtime 可能意外終止。若每次都等使用者手動確認，工作會長時間停滯；若無限制地自動重試，連續故障會被放大，也可能重複送出外部操作。

## 決策

採 B＋B1＋R2 N=3＋R2-A＋額度用盡後人工解除＋S2＋D1，限定同一次 Windows 使用者登入期間：

- Runtime 意外終止後再次啟動，先核對狀態，只自動恢復崩潰前允許執行且通過安全、授權、相依與版本檢查的工作。暫停、取消與完全退出意圖優先。
- 先對身分已確認的舊 Controller／Worker 保存證據並限時受控停止，確認 writer 停止後以**新 Run** 恢復並檢查新版授權與設定；安全相容時可恢復原生 Session。不得僅憑 PID 或 heartbeat 逾時終止程序或重派。
- 同一恢復事件最多三次自動嘗試（含第一次）；一次是完整的恢復嘗試，不是每個 Worker 各一次。第二、第三次前分別至少等待 30 秒、2 分鐘。程序停止或啟動副作用之前，先持久化事件與嘗試序號，無法保存就不開始。
- 完成必要核對與處置後，連續穩定 10 分鐘並持久化成功，才結束事件；觀察中再次崩潰沿用原事件與已用次數。
- 三次均未成功後持久化「恢復額度用盡」，停止自動恢復，保留診斷；重開 App、Runtime 重啟與額度恢復都不清除。使用者明確要求後才建立新輪次並保留歷史。
- 恢復計數與 Task 修正預算、額度交接分開。

Spec 補充（AI 暫定，待使用者確認）：D-16 暫定實作失敗 3 次、驗證不完整 2 次、基礎設施重試 5 次，與恢復計數互不混用；D-31 暫定 heartbeat 15 秒、lease 60 秒，過期 lease 只觸發核對，不證明程序死亡。

## 替代方案

- 每次人工確認：增加停滯。
- 存活 Run 直接接管：增加通道、事件與憑證恢復成本。
- 只嘗試一次：較難跨過暫態故障。
- 無上限或冷卻後自動重置：持續循環。
- 啟動即算成功：可能過早清空計數。
- 較長退避：延後診斷。

## 後果

- 恢復會中斷仍正常執行的舊 Agent，可能重做最近檢查點之後的部分工作，但不得盲目重送外部操作。
- 不保證崩潰期間 Agent 立即停止，也不消除所有週期性故障。
- 30 秒、2 分鐘、10 分鐘是已確認的產品政策值，不是 Windows 實測證明的最佳值；驗證不能靜默更改，必要變更另行審查。
- 自動重啟 Runtime 的機制由 [ADR-0006](0006-runtime-guardian.md) 補足，並把三次的計次起點提前。
