# ADR-0006：Runtime 輕量監護、共用恢復額度與監護降級

- 來源識別：DR-20261021-06
- 狀態：已確認（使用者核准，2026-10-21）；Windows 實作為 Validation Required，尚未驗證
- 來源：[issue #3](https://github.com/Anuise/issue-orchestrator/issues/3) §17 DR-20261021-06；§1.2、§2、§11.2、§11.4、§12.6、§15.8
- Spec 對應：[spec.md](../../.scratch/platform-rebuild-v1/spec.md) 的 D-24（監護與 Runtime 的銜接）、User Stories 79–81

## 背景

[ADR-0005](0005-runtime-crash-recovery.md) 規定了崩潰後的恢復，但沒有說明誰來重新啟動 Runtime。若只等使用者開 App，無人值守時會停滯；若分開計算「啟動」與「恢復」兩套額度，重置與組合上限都變複雜。

## 決策

採 B＋B1＋M1，限定同一次 Windows 使用者登入期間：

- 以獨立輕量的監護程序監看 Runtime；關閉桌面視窗不停止監護。監護不派工、不裁定、**不直接寫控制資料庫**，Runtime 仍是唯一控制平面。
- 只對「已確認意外終止」的 Runtime 做有限次自動重啟；不因 heartbeat 或 API 逾時就強制重啟。每次啟動前核對程序身分、單實例所有權、停止意圖與維護抑制；停止意圖不明時不推定允許啟動。
- **共用三次額度（B1）**：自動啟動、核對、恢復與穩定觀察共用同一事件的三次額度；監護在啟動前先持久化事件、輪次、嘗試識別與次數，Runtime 接續同一次，不另扣也不另取。啟動早期失敗也計次；無法保存或核對時不自動啟動。
- **降級（M1）**：監護自身終止時，正常的 Runtime 繼續工作，並顯示「工作繼續，自動重啟保護不可用」；下次開 App 只補缺少的元件，不重設次數、退避與阻擋。兩者皆死亡時等待使用者開 App。
- 三次用盡後停止自動重啟；診斷啟動只提供診斷，不恢復工作也不派工；使用者明確要求才建立新輪次。完全退出、更新與解除安裝抑制重啟。

Spec 補充（AI 暫定，待使用者確認）：D-24 暫定為監護只寫獨立的 append-only 日誌檔（每筆 fsync），Runtime 啟動時匯入控制資料庫並以嘗試識別去重；issue 明載儲存與銜接機制為 Validation Required。

## 替代方案

- 只等使用者開 App：無人值守時停滯較久。
- Windows 系統服務：增加部署、權限與 Session 協調。
- 分開的啟動與恢復額度：增加重置與組合上限的複雜度。
- Runtime 反向監護：增加雙向重啟與退出競態。

## 後果

- 三次可能全部耗在 Runtime 啟動早期失敗。
- 監護失效後，Runtime 若再死亡，要等使用者開 App；兩者皆死亡後不保證自救。
- 監護自動修復、無回應偵測與受控重啟、進階診斷留待後續。
- 此「監護」不同於 Runtime 內部管理 Agent 程序的 supervisor。
