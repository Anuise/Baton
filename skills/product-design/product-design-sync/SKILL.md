# 預覽、核准與同步

先讀 [共用契約](../product-design-review/references/context.md) 與 [Decision Record](../product-design-review/references/decision-record.md)。確認指定目標、候選記錄、審查基準、一致性結果與完成度。缺少前提則讀取 [決策 skill](../product-design-decision/SKILL.md)，回報缺漏；不將 `sync` 本身解讀為寫入授權。

## 預覽關卡

候選決策達 Ready for Approval 後，展示：完整 Decision Record、目標 Issue 與精確章節、修改前後差異、跨模組影響、增修驗收條件及尚未同步狀態。預覽以完整新本文或可重建完整本文的精確差異為準，保留無關內容。

詢問是否核准將「這份預覽」同步至指定 Issue。使用者對已展示版本與範圍的明確授權仍有效時直接進入寫前檢查，無須重複詢問。只選方案、要求預覽或單獨輸入 `sync` 不足以確認具體差異。核准後設計狀態為 Approved，同步狀態仍為 Pending。

## 寫前檢查

1. 重新取得 Issue 最新完整本文與全部留言，對照預覽基準的本文、更新時間與留言變化。
2. 檢查新增內容、取代紀錄與候選決策相容性。相同 ID 的候選版本／內容已存在時，先驗證是否本次提交已成功，避免重複寫入；若是既有舊版，僅修訂預覽指定記錄，保留 ID 與版本／取代關係。同義重複或內容衝突交由使用者裁定。
3. 沒有並行變更時只提交已核准的必要章節。若有並行變更，停止寫入、展示差異並取得重新裁定；不靜默合併後覆蓋。
4. 若 Connector 支援條件式更新／版本比對則使用；若不支援，說明讀寫之間仍存在競態的限制，緊接最新讀取執行一次寫入，不能宣稱有原子衝突保護。

## 寫入與驗證

使用可用 GitHub Connector 更新指定 Issue 本文；不以新增留言替代核准的本文修改，不修改其他 Issue、程式碼或建立 PR。

一次提交後重新讀取本文及必要留言，確認決策記錄、核准日期、相關章節、驗收條件與預期本文一致，並檢查無關內容未被覆蓋。若提交內容包含 Synced 標記，只有本次回讀確認後才認定它有效；不在驗證前對使用者宣稱成功。

工具回傳失敗、逾時或結果不明時先回讀查明是否已寫入，避免重複提交。無法確認或發現意外覆蓋時停止其他寫入，保留 Pending、顯示實際結果與差異；不自動重試或自行回滾別人的變更。權限不足或缺乏更新工具時，提供可貼入指定章節的完整內容與差異，明示未同步。

逾時後若確認已完整寫入，完成回讀驗證；確認完全未寫入則保留 Pending 並報告結果。本輪不自動重試；使用者後續明確要求繼續提交時，重新執行寫前檢查，沿用仍有效的具體核准。部分寫入或無法確認時先停止並釐清差異，不能把「繼續」當成任意覆蓋的授權。

## 同步後銜接

成功回讀後才標示 Synced，附 Issue 連結與驗證結果。更新受影響模組、解除的依賴、成熟度與優先級，推薦下一個可處理決策並等待選擇。模組關鍵決策完成則回模組列表；領域主要決策完成則回地圖，讀取 [探索 skill](../product-design-discovery/SKILL.md) 生成所需清單。同步不代表已實作、已測試或可發布。
