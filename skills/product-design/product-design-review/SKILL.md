# 產品設計審查流程入口

全程使用繁體中文。這是互動設計流程，不是自動完成所有決策的批次任務。

先讀 [共用規格與交接契約](references/context.md)。四個 skills 必須安裝於同一父目錄；相對路徑以本檔案所在目錄解析。階段轉移時，實際讀取對應 `SKILL.md` 並遵循它，不能只在回答中提及技能名稱。缺少檔案時指出缺少的依賴，不假裝已執行。

## 路由與前置條件

依使用者本輪意圖及可取得的交接狀態，選擇一個階段；只載入該階段需要的資料。

| 意圖／狀態 | 載入的 skill | 完成後的關卡 |
|---|---|---|
| 首次啟動且未指定範圍、`map` | [product-design-discovery](../product-design-discovery/SKILL.md)，領域模式 | 呈現完整地圖，等待選擇 |
| 指定領域、`domain ID` | 同上，模組模式 | 呈現模組清單，等待選擇 |
| 指定模組、`module ID` | 同上，決策模式 | 呈現決策清單，等待選擇 |
| 已選具體決策、`decision ID`、回覆當前決策問題 | [product-design-decision](../product-design-decision/SKILL.md) | 每輪一個核心問題，等待回答 |
| 候選決策已符合 Ready for Approval、`preview`、`sync` | [product-design-sync](../product-design-sync/SKILL.md) | 先預覽具體差異，再等本次同步授權 |
| 對已展示的具體同步預覽明確核准 | 同上，先檢查核准範圍及最新基準 | 寫後驗證，再推薦下一項供選擇 |

正常路徑：領域地圖 → 使用者選領域 → 模組清單 → 使用者選模組 → 決策清單 → 使用者選決策 → 逐輪審查 → 一致性與完成度驗證 → 修改預覽 → 使用者核准 → GitHub 同步驗證 → 更新依賴並推薦下一項。

使用者已直接指定具體模組或決策時，可略過較高層選單，仍須讀取最新規格、驗證項目與依賴。若範圍或 ID 無法唯一對應，先展示可辨識的候選項並釐清，不能猜測。選擇方案不等於核准所有子項；`sync` 只表示啟動確認流程。

## 導航

接受下列指令及同義自然語言；僅在本審查脈絡中解讀簡短命令。

| 指令 | 行為 |
|---|---|
| `back` | 返回決策清單、模組清單或領域地圖的上一層 |
| `status` | 顯示範圍、階段、設計與實作狀態、目前阻塞 |
| `dependencies` / `risks` / `unresolved` | 顯示當前範圍的依賴／風險／未決事項及來源 |
| `summary` | 整理當前討論、候選決策及未同步內容 |
| `review` | 載入 decision skill，檢查一致性與完成度；沒有候選決策時先指出缺漏 |
| `refresh` | 重讀來源，重新檢查目前範圍與依賴，不重設已存在的選擇 |
| `next` | 推薦下一個可處理項目，等待選擇 |

切換範圍前摘要尚未同步的候選決策；導航不構成核准。新對話或無法取得前文時，從 GitHub 重建已保存部分，明確指出未同步討論不可得。若使用者要求繼續遺失草稿，先請其提供目標 Decision ID 與候選內容／摘要；只取得 ID 時，交由 decision skill 依現存規格重新建立候選，明示這不是恢復原討論。補足前不進入同步，也不自行重做整張地圖。每輪結尾保留共用契約中的精簡交接狀態。
