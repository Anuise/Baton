SCOPE: web/、src-tauri/、scripts/、docs/、crates/baton-harness — Web UI、Tauri 殼、腳本、文件與 harness 測試（UI 行為、測試是否真的涵蓋驗收、文件與實作一致）
FINDINGS:
- [中] 授權面板在切換 Workspace 時，較慢回來的舊回應會蓋掉新 Workspace 的草稿。`load()` 沒有防過期回應的保護，`App.tsx` 也沒有用 `key` 讓面板隨 Workspace 重新掛載。最壞情況：使用者先點 A 再點 B，A 的回應晚到，畫面標題是 B、草稿卻是 A 的 grants，按「確認並保存授權」就把 A 的授權（可能更寬）寫進 B。`TaskBoard`、`DecisionCenter`、`ArtifactsPage`、`KnowledgePage`、`ModelOverridesPanel` 也是同樣寫法，同樣沒有 key — `web/src/AuthorizationPanel.tsx:78`、`web/src/App.tsx:104-115` — 這幾個元件都比照 Timeline／Verification 等頁加上 `key={opened.workspace.id}`，或在 `load` 裡用 cancelled 旗標或 latest ref 丟掉過期回應；並補一個「先選 A 再選 B、A 較晚回應」的元件測試。
- [中] 系統匣「完全退出」啟動的 60 秒後備計時器無法取消。使用者在 `ExitProgress` 的失敗畫面按「返回」放棄退出後，計時器仍會送出 `request_exit` 並執行 `app.exit(0)`；連按多次還會疊加多個計時器。這違反使用者的選擇 — `src-tauri/src/main.rs:956-965`、`web/src/ExitProgress.tsx:136-138` — 把計時器存成可取消的 handle（例如放在 `RuntimeLink` 的 `Mutex<Option<JoinHandle>>`），Web UI 確認已送出請求或按「返回」時通知殼端取消；重複按下時不再另起計時器。
- [中] `ensure_started` 用 `OnceCell` 永久快取啟動結果，連失敗結果也一起快取（例如 `START_WAIT` 逾時、資料目錄檢查失敗）。Runtime 隨後就算已經正常監聽，App 存活期間約 90 個指令也都只會回同一個錯誤，必須重開 App 才能恢復 — `src-tauri/src/main.rs:119-139` — 只快取成功結果（例如改用 `tokio::sync::Mutex<Option<Connection>>`，失敗不寫入），下次呼叫再重試。
- [中] 更新進度畫面可能依據過時的停止結果自動安裝。輪詢看到 `maintenance=ready` 時，如果 `lifecycleStatus` 讀取失敗，`lifecycle` 會保留 stopping 階段讀到的舊值，`hasLifecycle` 仍為 true，`canAutoInstall` 就會成立，略過最終才出現的停止異常。這與註解所說「看到準備套用後讀到的停止結果才是最終的」不符 — `web/src/UpdateProgress.tsx:34,45-50,71` — 另外記錄「ready 之後才讀到的 lifecycle」（例如 `lifecycleAfterReady` 旗標），`canAutoInstall` 只看這份。
- [中] 更新時如果 Runtime 在 UI 輪詢到 `ready` 之前就結束了，之後每次 `updateStatus` 都會失敗。phase 會永遠停在 stopping，畫面也沒有任何安裝或關閉按鈕；殼端的 `update_install` 其實能處理 Runtime 已無法連線、只剩 `ready_package` 的情況，使用者卻無從觸發 — `web/src/UpdateProgress.tsx:45-53` — 輪詢連續失敗時，向殼查詢是否記得 `ready_package`，有的話提供「安裝更新」按鈕。
- [中] 完全退出時，`lifecycleStatus` 只要失敗一次就被判定為 `runtime_gone`，1 秒後 `quitApp`。暫時性的逾時或 5xx 會讓使用者看不到之後才出現的停止異常清單（spec D-11／D-25 要求列出異常） — `web/src/ExitProgress.tsx:96-98,108` — 改成連續失敗 N 次，或確認連線已被拒絕，才判定為 runtime_gone。
- [中] spec D-21 規定頂部狀態列要固定顯示「可用帳號數」，但 `StatusBar` 只顯示 Runtime、平台、待裁定數、恢復事件、監護與儲存故障，沒有帳號數。ai-decisions 裡也找不到改變這條的決策 — `web/src/StatusBar.tsx:34` — 從 `scheduling` 或帳號總覽算出可派帳號數並顯示，或在 ai-decisions 補一條決策說明為何省略。
- [中] spec「Testing Decisions 3」要求以 Playwright 做少量 UI E2E：首次精靈、派工到完成、裁定中心批次處理、完全退出進度、恢復事件顯示。目前只有 `smoke-desktop.mjs`，涵蓋啟動、關窗後重連、精靈、建立 Workspace 與授權；其餘四條旅程沒有任何 E2E。AI-?（ai-decisions.md:306）寫「UI E2E 是後續票的範圍」，但 01～52 號票中沒有任何一張承接 — `scripts/smoke-desktop.mjs:167-292`、`.scratch/platform-rebuild-v1/ai-decisions.md:306` — 擴充冒煙腳本涵蓋這四條旅程，或開票、在 spec 註記延後。
- [低] 冒煙腳本的 `finally` 沒有結束 `app1`／`app2`。如果在取得 `runtimePid` 之前就失敗（例如步驟 1 等待逾時），`baton-desktop.exe` 與它拉起的 Runtime 都會殘留，`rmSync` 也可能刪不乾淨 — `scripts/smoke-desktop.mjs:296-307` — 把 app1、app2 提到 try 外宣告，在 finally 一併 `killProcess`；取得 runtimePid 前失敗時，改從 health 或資料目錄找 Runtime PID。
- [低] 真實瀏覽器的情境測試在本機沒有 Playwright 時只印出訊息就 `return`，結果會顯示為「通過」。文件只對 `browser_driver.rs` 說明「沒有 Playwright 時略過」，沒提到這個 harness 測試，CI 綠燈也無法代表 web 驗證 Adapter 有被實測 — `crates/baton-harness/tests/web_verification_real_browser.rs:150-156`、`docs/development.md:1268` — 改成 `#[ignore]` 並以環境變數啟用（比照 adapter_contract），或至少在 docs 註明這個測試在無 Playwright 時會靜默通過。
- [低] 部分 harness 情境測試用了真實的 `tokio::time::sleep` 等待，與 spec「時間一律由 fake Clock 控制，不使用真實 sleep」不一致，也是潛在的偶發失敗來源（可與 review-notes #2 一起查） — `crates/baton-harness/tests/lifecycle.rs:409,455`、`crates/baton-harness/tests/worktrees.rs:275`、`crates/baton-harness/tests/claude_adapter.rs:121,263` — 改為等待可觀察的條件（notify 或事件），不要依賴固定毫秒數。

SUMMARY: 這個範圍的 Tauri 殼、安裝掛勾、CSP、桌面憑證的處理，以及「瀏覽器開發模式會被 403 拒絕」的說明，都與 ADR 和 docs 一致，註解也都是繁體中文。問題主要集中在 UI 的非同步邊界：切換 Workspace 時過期回應覆寫畫面（可能把授權寫錯 Workspace），以及退出與更新流程對暫時性失敗、使用者取消的處理不夠穩健。測試面上，harness 情境測試大致忠實走主要 seam，但 spec 要求的 UI E2E 旅程大多沒有涵蓋，D-21 的「可用帳號數」也沒有實作。另外說明：crates/baton-harness 與 docs 只做了抽樣與交叉比對，沒有逐檔細讀；review-notes 已列的項目沒有重複回報。
